But who would do such a thing?

We don't have to do much detective work to figure out the culprit. 
Our <Hint message="After all, that's the only thing our shader does!">main suspect</Hint> is _the rotation function_!

```glsl
vec2 new_uv = vec2(
    //🏃‍♀️💨 You'll never catch me alive! 
    UV.x * cos(angle) - UV.y * sin(angle),
    UV.x * sin(angle) + UV.y * cos(angle)

```

Everyone leaves a trace, and in our case, the top-left corner is awfully suspicious!
I think it's time for some questioning.

#### Why is the top-left corner not moving?

<Separator />

At that point our UVs have the value `(0, 0)`. 
There's nothing inherently special about these coordinates, but for our function, something interesting happens if we replace the UVs with them:

```glsl
vec2 new_uv = vec2(
    0.0 * cos(angle) - 0.0 * sin(angle),
    0.0 * sin(angle) + 0.0 * cos(angle)
);

// Let's hear this point's confession:

vec2 new_uv = vec2(0.0, 0.0);
```

From whatever <Hint message="Pun, very much, intended!">angle</Hint> you look at it, in the corner, the new UVs remain the same as the initial UVs: `(0.0, 0.0)`.

Visually, a UV value that stays the same, that doesn't change, is a value that will show no movement, which is exactly what we see when we try <Hint message="I'd show the shader again, but I don't want him to get dizzy.">rotating our Cashew</Hint>. 

Hmm.. so if we could find a different function, one that stays fixed at `(0.5, 0.5)`, the rotation _pivot_ would be in the center.
<Align align='center'><h5>Case Solved!</h5></Align>

Now, what remains is to find that function to help Cashew rotate from the center, as initially intended.

But you probably noticed something a bit unnatural about that second step. 
Instead of moving my hand to the middle of the paper like a normal person, I _moved the paper to my hand_. Why?

Because my hand was sitting perfectly comfortably, and I didn't want to move it.

In shaders, we like to be as comfortable as possible. 
Our rotation formula feels so much better when it doesn't have a bunch of numbers scattered around. Why ruin its zen? 

We already know how to move the canvas around from the previous lesson. Why don't we use that to shift it so its center lands in (0.0, 0.0)?

The only caveat is that in real life, if you move the paper slightly, you still see it. Like.. it's in your hand.<br/>
In shaders, though, we can only see a limited region of our canvas. So when we move it, the image is no longer fully in frame.

Let's get back to Shader World and <Hint message="I think I've accidentally created an optical illusion. While Cashew rotates, look for a few seconds at its center. If you quickly look somewhere else there's a cool twisting effect. Fun!">see this</Hint> in practice:

  width={260}
  showCode={true}
>
{`void fragment() {
    float angle = TIME;

    // We already know how to translate our canvas
    // Slide the UV from [0, 1] to [-0.5, 0.5]
    // The UV is now centered in (0, 0)
    vec2 centered_uv = UV - vec2(0.5, 0.5);

    // Rotate using the simpler formula
    vec2 rotated_uv = vec2(
        centered_uv.x * cos(angle) - centered_uv.y * sin(angle),
        centered_uv.x * sin(angle) + centered_uv.y * cos(angle)
    );

    // Move back the UV to keep the sampled texture in view
    // UV goes from [-0.5, 0.5] back to [0, 1]
    vec2 new_uv = rotated_uv + vec2(0.5, 0.5);

    COLOR = texture(TEXTURE, new_uv);

    // ... discarding logic
}`}
</ShaderPreview>

I'm much happier with our code now:
- It's **readable**: The events are separated. We pick a pivot, rotate around it, then move back into view.
- It's **straightforward**: The rotation formula stays in its simplest form. We do not pollute it with the pivot math.
- It **feels natural**: If we want to change the rotation, we change the formula. If we want to change the pivot, we write a different translation value.
- It **feels great!**

We can use the `distance()` function to figure out how far the current pixel is from the center `(0.5, 0.5)`.<br/>
If the pixel is reasonably close (let's say... less than `0.04`), then it's inside the circle.

The tools to solve this are many. We could go with an if statement, a ternary operator, a step or even a smoothstep if you like your circles well done. Let's go with `step()` and use the result in our red channel.

<ShaderPreview
  sprite={cashew}
  fullShader={`void fragment() {
    float dist = distance(UV, vec2(0.5, 0.5));
    float circle = step(0.04, dist);
    COLOR = vec4(circle, 0.0, 0.0, 1.0);
}`}
  width={260}
  showCode={true}
/>

I'm getting flashbacks from my childhood, because we colored outside the lines. 

The `step()` function returns `0.0` for values smaller than the set edge, and `1.0` otherwise. That's why we end up coloring only values _outside_ the circle.
We can easily flip the result by subtracting it from `1.0`.

<ShaderPreview
  sprite={cashew}
  fullShader={`void fragment() {
    float dist = distance(UV, vec2(0.5, 0.5));
    float circle = 1. - step(0.04, dist);
    COLOR = vec4(circle, 0.0, 0.0, 1.0);
}`}
  width={260}
  showCode={true}
>
{`void fragment() {
    float dist = distance(UV, vec2(0.5, 0.5));
    // Alternatively we could've swapped the arguments: 
    // step(dist, 0.04) Think about why that works.
    float circle = 1. - step(0.04, dist);
    COLOR = vec4(circle, 0.0, 0.0, 1.0);
}`}
</ShaderPreview>

<ShaderPreview

#### The pivot is not the point

<Separator />

Alright, being able to choose the point from which we transform our UV is a nice example of what we can do in order to make our life easier. However, despite holding the name of the lesson, _the pivot_ is not the point.

> The point of this chapter is learning how to make our life easier

It's not only the pivot we can change to achieve that. For example, when it comes to shaders, there's a lot of trigonometry involved.
Most functions that deal with angles, such as `sin` and `cos`, are easiest to understand and work with on the _unit circle_, which is centered in `(0.0, 0.0)` and which ranges on both axes between `[-1.0, 1.0]`.

We know how to make our lives easier by sliding the UV pivot to `(0.0, 0.0)`, but after we finish sliding, the UVs range between `[-0.5, 0.5]`. 
We could stop here, but nobody is prohibiting us from making our lives even easier. We can also scale our UV, multiply it by 2.0, so that it lands between `[-1.0, 1.0]`, and that is going to prove very useful in our next lesson in which we'll learn how to **treat functions as brushes** and get rid of most math you'll see in any future shaders.
