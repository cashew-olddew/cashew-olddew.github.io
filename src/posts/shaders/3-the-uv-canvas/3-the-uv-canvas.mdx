#### Movement

<Separator />

Let's create a moving shader! Meet Cashew, my assistant!

<Media width={200} label='Cashew'>
  <img src={cashew} alt="Cashew OldDew" />
</Media>

Right now, Cashew is just an image. A flat grid of colored pixels, unable to show his unending excitement.
To bring him into Shader World, our fragment shader needs to answer the same question it always does: 

"What color should the current pixel be?"

Except this time, instead of calculating the answer ourselves... we make sure no one's looking and copy it from the texture.

That's <Hint message="The next time you get caught, just tell the teacher you were texture sampling. Works every time!">**texture sampling**</Hint>!

To do that we use a shader built-in function, unsurprisingly called `texture()`. 
With it, each fragment uses its *UV* coordinates to find the corresponding point in the image.

For example, a fragment at (0.2, 0.3) looks 20% across and 30% down the texture and picks the color it <Hint message="Sometimes, that percentage might not perfectly align with a pixel's coordinate. In such cases, Godot relies on the object's filter mode to 'guess' the color of the pixel. This leads to the canon event we all went through where pixel art looks blurry, which happens with the 'linear' filter mode, because we're mixing large sprites with small textures!">landed on</Hint>.

<Media width={360} label='Pixel Sampled from Cashew'>
  <img src={cashewSample} alt="Pixel Sampled from Cashew" />
</Media>

And again, remember that the UVs are just percentages. 
The scale of either the object or the texture does not matter in this case. 
A UV value of 0.2 will always sample a value 20% inside the texture.

_"But wait, how does the shader even know we want to sample Cashew?"_

Most nodes you'd likely apply shaders on will have a texture property. Godot gives us that property through the `TEXTURE` built-in. How convenient!

So now, putting it all together, my dear assistant is going to... 

<Hint message="There was supposed to be a magic wand here, but it doesn't work on all systems. Cashew appeared, but the wand is gone. The universe gives, the universe takes.">Appear in Shader World!</Hint>

<ShaderPreview
  sprite={cashew}
  fullShader={`shader_type canvas_item;

void fragment() {
    COLOR = texture(TEXTURE, UV);
}`}
  width={200}
  showCode={true}
/>

We just wrote the shader Godot is applying by default to all 2D nodes using textures.

This is great progress, but Cashew still isn't moving. How could we solve this?

Well, we can't tell a pixel to move, a pixel is a pixel, it's just a small light glowing with color.
What we _can_ do is to tell the pixel to sample a different color, one that comes from somewhere else in the texture.

For example, let's see what happens if we tell our pixels to sample with a `0.5` offset to the right:

<ShaderPreview
  sprite={cashew}
  fullShader={`void fragment() {
    // We can access parts of a vec with
    // either (x,y,z,w) or (r,g,b,a)
    // we already did this for colors
    vec2 new_uv = vec2(UV.x + 0.5, UV.y);

    COLOR = texture(TEXTURE, new_uv);
}`}
  width={200}
  showCode={true}
/>

No, your screen is not broken. This is actually what we expect to see, but there are <Hint message="Okay, more like two questions, but they're big questions!">so.. many.. questions</Hint>!

First of all, didn't we say we're going to have an offset to the _right_? We literally added `0.5` to our coordinates. Why did the image move left?

Let's take an example: 
The top-left corner has the UV coordinates `(0.0, 0.0)`, so by adding the horizontal offset, it samples the color at `(0.5, 0.0)`, which is the highest point at the middle of our texture.
If we apply the same rule for each pixel, we end up with a sampling that looks something like this:

<Media label='Texture sampling with a 0.5 horizontal offset' width={360}>
  <img src={sampleOffset} alt="Texture sampling with a 0.5 horizontal offset" />
</Media>

Okay, but that still doesn't explain the weird glitch effect that's happening to the other half.

Let's take another example: 
The pixel at the top-right corner has the coordinates `(1.0, 0.0)`. This time, the horizontal offset takes us to `(1.5, 0.0)`, which lands outside the <Hint message="Remember! We get the texture pixels, or texels, for short, only with UV values ranging between (0.0, 0.0) and (1.0, 1.0).">texture's bounds</Hint>.
Similarly, all pixels with the x coordinate larger than 0.5 land in this same region. So, what happens when a shader tries to sample outside of a texture?

<Media label='The sampled region outside the texture' width={360}>
  <img src={regionOutside} alt="The sampled region outside the texture" />
</Media>

Well, it depends. Similarly to how there's a filter mode property for every <Hint message="Found in Inspector > CanvasItem > Texture.">texture</Hint>, there's also a repeat mode property which tells the shader how to behave when sampling values _outside_ the texture's range.

<Media label='Filter and Repeat mode texture settings'>
  <img src={repeatModes} alt='Filter and Repeat mode texture settings' />
</Media>

By default, the texture doesn't repeat. Because of that, Godot effectively clamps the coordinates to the edge of the texture.
So, for our example, when our coordinates became `(1.5, 0.0)`, the shader treated them as (`1.0, 0.0)`. Applying that to all other pixels in this region leads to the striped glitchy image we see.

The other repeat modes do pretty much what you'd expect:

<MediaGroup align='center'>
  <Media label='Repeat Mode: Enabled' width={260}>
    <img src={repeatEnabled} alt='Repeat Mode: Enabled' />
  </Media>
  <Media label='Repeat Mode: Mirror' width={260}>
    <img src={mirrorEnabled} alt='Repeat Mode: Mirror' />
  </Media>
</MediaGroup>

But getting back to our non-repeating texture, we can easily get rid of the weird lines by discarding pixels with coordinates that would sample outside the texture.
And yes, this follows the same obvious naming pattern, as we just have to write `discard`.

<ShaderPreview
  sprite={cashew}
  fullShader={`void fragment() {
    vec2 new_uv = vec2(UV.x + 0.5, UV.y);

    COLOR = texture(TEXTURE, new_uv);

    // I won't add this code block 
    // in future examples for brevity
    if (
      new_uv.x < 0.0 || new_uv.x > 1.0 ||
      new_uv.y < 0.0 || new_uv.y > 1.0
    ) {
      discard;
    }
}`}
  width={200}
  showCode={true}
/>

Finally, movement can't really be called "movement" if we just teleport Cashew to a different position.

This time, however, because we looked at UVs from a different lens it was so much easier to understand why changing it behaves the way it does. 

It's true that UVs are the coordinates of a fragment, and yes, if we apply some change and calculate it, the math checks out, but you can generally verify with math only after you've come to a solution.
When building shaders, you don't have the solution ahead of time. So instead, what we need to know is:<br/>What does changing these UVs **mean** for the overall shader?

Changing the UVs is like changing the _canvas_ of your shader artwork. 

UVs are your canvas!

##### 2. Repeat

Who ordered 9 canvases? I'm not paying for that!

You know how our texture gets sampled when coordinates land between _0.0_ and _1.0_?
Well, who's to say you can't land there multiple times? What if every time we reached the edge of our interval, we started from the beginning?

That's exactly what the `fract()` function does. It keeps only the decimal part of the number, so values like _0.5_, _1.5_ and _2.5_, all become _0.5_.

In the next example, scaling the UVs by `3.0` and wrapping with `fract()` tiles the canvas into a 3x3 grid of repeating copies.

<ShaderPreview
  sprite={cashew}
  fullShader={`uniform vec2 repeat = vec2(3.0);

void fragment() {
    vec2 new_uv = fract(UV * repeat);

    COLOR = texture(TEXTURE, new_uv);
}`}

##### 5. Rotate

When rotating, every point in the image traces its own circular path.
What the <Hint message="We'll see later how to intuitively find it.">formula</Hint> does is to get the x and y coordinates that land on that circle of rotation.
For now we don't need to worry about _how it works_. All that matters is that we have something like:

```glsl
vec2 new_uv = vec2(some_circle_coordinate.x, some_circle_coordinate.y);
```

Let's make the angle of rotation vary with TIME as well, so that our movement dedicated chapter has at least three shaders actually moving.

<ShaderPreview
  sprite={cashew}
  fullShader={`void fragment() {
    float angle = TIME;
    vec2 new_uv = vec2(
        UV.x * cos(angle) - UV.y * sin(angle),
        UV.x * sin(angle) + UV.y * cos(angle)
    );

    COLOR = texture(TEXTURE, new_uv);

    if (
      new_uv.x < 0.0 || new_uv.x > 1.0 ||
      new_uv.y < 0.0 || new_uv.y > 1.0
    ) {
      discard;
    }
}`}
  width={260}
  showCode={true}
>
{`void fragment() {
    float angle = TIME;
    vec2 new_uv = vec2(
        UV.x * cos(angle) - UV.y * sin(angle),
        UV.x * sin(angle) + UV.y * cos(angle)
    );

    COLOR = texture(TEXTURE, new_uv);

    // ... discarding logic
}`}
</ShaderPreview>

No need to worry, the shader is not broken. We just have to wait for Cashew to spin around the `(0.0, 0.0)` coordinate.

You probably expected the rotation to happen from the center of the canvas, around `(0.5, 0.5)`, and of course, with some hard work, we could find a formula that gives us that.
If my plan was to make you leave the course as fast as possible, that would've been an effective strategy.

It's true that there's some math in our shaders, but we can at least keep it clean and pretty.
We'll see that the more our parameters are <Hint message="I mean this quite literally! If a parameter is 0, it doesn't exist!">zeroes and ones</Hint>, the easier it becomes to wrap our heads around what's going on in an example. 
That's why I like keeping the center `(0.0, 0.0)` in this case.
