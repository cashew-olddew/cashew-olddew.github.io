#### What is a shader?

<Separator />

A shader is just a program. 

You use it to tell your graphics card how something should appear on the screen.
In fact, every single object you see on your screen in Godot is already using a default shader and its behavior is exactly what you'd expect: it just draws the texture normally.

To "draw" something, the GPU goes through a **series of predefined steps** which take that 'something' and turns it into real pixels on the screen.

By writing your own shaders, you can change the default behavior of some of those steps. The two you will often hear about are the **vertex** and **fragment** shaders.

#### The Vertex Shader

<Separator />

Everything needs to have a shape.
Vertices are the points that define that shape. 

Your first thought might be: _"Ah, just like in a 3D model! That has vertices!"_. And you'd be entirely right.

#### The Fragment Shader

<Separator />

Once the shape's settled, we need to color it.
Fragments are the tiny pieces that <Hint message="For most purposes, consider fragments and pixels being the same thing. We'll delve deeper into the differences in a future post.">will end up being</Hint> the final pixels on your screen.

By default, the GPU is just <Hint message="There are exceptions, such as that cool GPU you got!">as boring as before</Hint>: it takes the object's original texture and places it onto its _shape_.
The fragment shader allows us to change (quite drastically, if we please) the color of each pixel in our shape.

All the code of a fragment shader goes inside a `fragment()` function:

```gdshader
void fragment() {
  // This is where we'll build our portal
}
```

Let's make a blue thing, then!

A color is generally represented through four channels: <Color hex="#EE1111">Red</Color>, <Color hex="#11BB11">Green</Color>, <Color hex="#1111EE">Blue</Color> and <Hint message="This one is used to specify the color's transparency">Alpha</Hint>.
In Godot shaders, these values range between 0 and 1, with '0.0' meaning that a color is fully absent and '1.0' meaning that it's fully <Hint message="🎁">present</Hint>.

With this in mind, each color amount is a floating point number. We can define these inside a shader like this:

```gdshader
// Each shader also needs to specify its type
// `canvas_item` is for 2D and `spatial` is for 3D
// For brevity I won't mention it again in future code snippets
shader_type canvas_item;

void fragment() {
  float red = 0.15; // A tiny bit of red
  float green = 0.55; // Some more green
  float blue = 1.00; // A larger amount of blue
  float alpha = 1.0; // The portal is fully opaque
}
```

Also, it's generally a good idea to group together related information, so this could be more tightly rewritten as a <Hint message="There are also variants for grouping two and three numbers together with vec2 and vec3">vec4</Hint>:

```gdshader
void fragment() {
  // To get the expected color we need to place in order, 
  // the value for Red(r), Green(g), Blue(b) and Alpha(a)

  vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);
}
```

#### Built-in variables

<Separator />

What do you think Built-in variables are? You're a smart peanut! Write it down in this text field:

<Align align="center"><input type="text"></input></Align>

Alright, the text field <Hint message="Well, it technically does keep you engaged in the learning process, so it's quite valuable. Give it a ':)' as a sign of thanks!">does absolutely nothing</Hint>, 
but you probably figured out from their name that Built-ins are, well... variables that are _built in_, provided to us before we get to write even a single line of code.

These special variables serve two main purposes:
- **They provide context to us**: Giving us handy information like <Hint message="Tells us the time since the engine started">TIME</Hint>, <Hint message="Tells us the current Vertex position relative to the object (in local space)">VERTEX</Hint> or <Hint message="Gives us a sweet dessert!">PI</Hint>
- **They help us provide context to the GPU**: Giving us places to drop our data, like <Hint message="Lets us tell the GPU what color we want the current pixel to have">COLOR</Hint> or <Hint message="Yes, again! Some built-ins allow us to both read and write to them">VERTEX (again?)</Hint>.

There are lots of other Built-ins that we're going to unlock as we expand our knowledge through this course, but for now, let's focus on the `COLOR` built-in, so that we can tell the GPU to draw our portal color.

Your first instinct, especially if you've done any kind of traditional programming before, might be to write something like this to fill the portal:

<div className="prose-error-code">
```gdshader
// This is NOT how shaders actually work!
void fragment() {
  vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);

  // Go through each pixel to assign its color
  for(int x = 0; x < object_width; x++) {
    for(int y = 0; y < object_height; y++) {
      COLOR[x][y] = portal_color;
    }
  }
}
```
</div>

This is how I thought about it when I first learned shaders.

I mean, it makes sense: 
 - you grab the canvas
 - loop over its width and height
 - and then color every single pixel one by one

Things are quite different when writing shaders.<br/>
A key thing to understand is that you're not writing code for the whole image. You're writing code for <Hint message="Or for a single vertex if you're in the vertex() function!">a single pixel</Hint>! That exact same code is run by the GPU **at the same time** for every other pixel.

In the words of Pixel #16152:

> I have never met the pixel next to me.<br/>
> I do not know their place, or what they do,<br/>
> For neither they, nor I came first to be.<br/>
>
> Yet far beyond my narrow, lonely view,<br/>
> The selfsame code ignites another light,<br/>
> We're all in isolation, separate and blue,<br/>
> Yet painting the same picture, perfectly aligned.<br/>

If you sit with that for a moment, everything starts to make sense. 
Our pixel doesn't need to know what the rest of the canvas looks like, and even if it wanted to, it couldn't.
All it needs to do is follow its own rulebook. In our case, it should simply accept its blue fate: 

```gdshader
void fragment() {
    vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);
    
    // The current pixel should have the portal color!
    COLOR = portal_color; 
}
```

And just like that, we have our blue thing!

But wait, if the same code runs for each pixel, then how can we make two pixels look different?

Well, a pixel doesn't know anything about other pixels, but it definitely knows _itself_.
We can tap into that knowledge through the Built-ins we just talked about.<br/>
For example, what's the difference between a pixel inside the portal and one outside it?

It has to be the pixel's position. To get the position of the current pixel, Godot provides us with the `UV` Built-in!

#### UV

<Separator />

I pretty much spoiled it in the last paragraph that UV tells us where a pixel is. Specifically, it gives us its horizontal and vertical coordinates.
Since we get two of these coordinates, naturally, the UV will be a `vec2`.

Now, what's interesting about these coordinates is that they do not provide exact pixel counts like `x: 32, y: 64`.
Instead, the UV coordinates are <Hint message="You might be getting a sense of Deja Vu, as for the colors we similarly had percentage based properties. You'll see this pattern make its appearance quite often. Shaders really love percentages!">percentage based</Hint>, with the value '0.0' meaning "the start"  and the value '1.0' meaning "the end".<br/>

There is a method to this madness, though. Percentage-based coordinates mean the shader doesn't care about the object's size. 
Whether the object is as small as a peanut or as large as a coconut, if the UVs of the current pixel are `vec2(0.3, 0.6)`, it still means the pixel is positioned 30% horizontally and 60% vertically.

Okay, but how could we visualize these coordinates to understand what the intentionally abstract "start" and "end" mean?<br/>
If you've ever debugged a program before, you've probably used the obviously superior form of printing out values to the console.
Shaders do not allow that. Since the code is run for every single pixel in a fragment, you'd probably flood your terminal with <Hint message="Also printed in random order, as the GPU does everything in parallel.">thousands of coordinates</Hint>, anyway.

However, shaders have a charming way of debugging:<br/> 

<Align align='center'><h5>By visualizing values</h5></Align>

<Separator />

We can take the `x` coordinate of our `UV` and apply it to the <Color hex="#EE1111">red</Color> channel of our result.<br/>
Then, we do the same with the `y` coordinate, but apply it to the <Color hex="#11BB11">green</Color> channel.

The result is going to be a beautiful, mango-colored square:

<ShaderPreview 
  fullShader={`void fragment() {
    COLOR = vec4(UV.x, UV.y, 0.0, 1.0);
  }`} 
  width={150}
  />

If you look closely at the mango square, you'll notice a few things:
- The top-left corner is fully **black**
  - This is where both x and y _start_, so both coordinates are 0.0.
- The top-right corner is fully <Color hex="#EE1111">red</Color>
  - This means <Hint message="Remember, we assigned x to the red channel">x</Hint> is 1.0.
- Similarly, the bottom-left corner is fully <Color hex="#11BB11">green</Color>
  - This means <Hint message="You don't need a reminder for y as well, I made this hint to tell you you're doing great!">y</Hint> is 1.0.
- Finally, the bottom-right corner is <Color hex="#FACA00">yellow</Color>
  - This is what happens when red and green combine, when both x and y reached their _end_ value, 1.0.

You just learned a fact about the UV coordinates by looking at a fruit-colored square!<br/>

The UV coordinates use the top-left corner as their origin `(0.0, 0.0)`:
- x increases towards the right
- y increases towards the bottom

#### Built-in functions

<Separator />

Since our UV coordinates map the top-left corner to `(0.0, 0.0)` and the bottom-right corner to `(1.0, 1.0)`, then the exact center of our canvas sits at `(0.5, 0.5)`.

So, say we have a maximum radius of 0.1 for our portal. Then, every pixel needs to ask itself:<br/>
"How far away am I from that center point?".<br/>
**If** it is further than 0.1, it's outside the circle. **Otherwise**, it's inside.

We already know exactly **where** the pixel is thanks to our UV coordinates. Now we just need a way to find the size of the gap to the center.

Luckily, variables are not the only tools Godot gives us. We also have a bunch of built-in functions designed to answer these exact kinds of questions.

For example, the `distance(thing, other_thing)` does exactly what it sounds like: gets the distance between two things.

Let's use it:

<ShaderPreview 
  fullShader={`void fragment() {
    vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);
    float dist = distance(UV, vec2(0.5, 0.5));

    if (dist > 0.1) {
      COLOR = vec4(0.0, 0.0, 0.0, 1.0); // Black
    } else {
      COLOR = portal_color;
    }
  }`} 
  width={150}
  />

"What is this, a portal for ants?"

Fair question! Right now, our portal is so tiny that not even your left foot could fit through it. 

To change the radius, you *could* manually open up the code, change that `0.1` to a `0.4`, and save it. But doing that constantly gets exhausting, especially as our shader grows more complex.<br/>
It's even worse when a <Hint message="That teammate could be future you!">teammate</Hint> needs to use your shader, as they'd have to dig through the raw code just to make a circle a little bigger.

There's a better way:

#### Uniforms

<Separator />

Godot allows us to declare variables that are accessible to the outside world.<br/>
This means you can tweak these directly in the Inspector, without touching the code.

To use this power, just add `uniform` in front of the variable declaration, placing it outside the `fragment()` function, usually near the top of the shader.
For our portal radius, it looks like this: `uniform float portal_radius;`.

We can also give Godot a _hint_ about a uniform's possible values. Let's set a reasonable range for our <Hint message="Different variable types can have different hints. We'll see more of them soon!">float</Hint> with `hint_range(start, end)`!<br/>

<ShaderPreview 
  fullShader={`uniform float portal_radius : hint_range(0.0, 1.0) = 0.1;

  void fragment() {
    vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);
    float dist = distance(UV, vec2(0.5, 0.5));

    // We compare to the uniform instead of the plain 0.1 value!
    if (dist > portal_radius) {
      COLOR = vec4(0.0, 0.0, 0.0, 1.0); // Black
    } else {
      COLOR = portal_color;
    }
  }`} 
  width={150}
  controls={
    { "portal_radius": {label: "Portal Radius", type: "float", min: 0.0, max: 1.0, default: 0.1}}
  }
/>

<Align align='center'>Drag the slider to make the portal human-sized!</Align>

Also, let me <Hint message="&elephant. Phew, that was easy!">address the elephant</Hint> in the room.<br/>
If you've spent any time reading shader tips online, you might have heard a scary rumor:<br/>
"Never, under any circumstance, use IF statements! It ruins performance! Every time you do that a puppy will cry!"

This, is mostly [an outdated myth](https://iquilezles.org/articles/gpuconditionals/).

For simple choices like the one in our example, modern GPUs are incredibly smart and have ways of avoiding slowdowns.<br/>
Especially while learning, do not be afraid to write if statements if you need them!

That's a much better circle!<br/>

But the **problem** now is that it has lost all its color.
Let's ask another **question**: How can we make our prettier, black and white image of a circle take the portal's color?
The **tool** is multiplication.

No kidding! We simply have to multiply the obtained `circle_shape` with the `portal_color`. But why does that work?<br/>
Remember how we represent colors: 0.0 is the absence of a color and 1.0 means the color is fully there.
When all three RGB channels are 0.0, we get black. When they're 1.0, we get white.

So then, the black and white image can act as a _mask_ for our color. Where there's white, the color is multiplied by '1.0', so it just stays.
Over the black zones, however, each color channel is multiplied by 0.0, so we're simply not going to have any color there.

Another thing you might've noticed is that the circle we've generated is black when `Radius 0` is smaller than `Radius 1`. 
We should flip the smoothstep radius edges to have it the other way around.

<ShaderPreview 
  fullShader={`uniform float portal_radius_edge0 : hint_range(0.0, 1.0) = 0.30;
  uniform float portal_radius_edge1 : hint_range(0.0, 1.0) = 0.33;

  void fragment() {
    vec4 portal_color = vec4(0.15, 0.55, 1.00, 1.0);
    float dist = distance(UV, vec2(0.5, 0.5));

    float circle_shape = smoothstep(
      portal_radius_edge1, // Edge 1 is now first!
      portal_radius_edge0,
      dist
    );

    // '.rgb' gives us only the red, green and blue channels
    // You could even write '.brg' to get them in a different order
    // That's called *vector swizzling*
    vec3 circle_color = portal_color.rgb * circle_shape;
    COLOR = vec4(circle_color, 1.0);
  }`} 
  width={150}
  controls={

    }
  }
/>

But the **problem** now is that it's completely frozen.<br/>
The **question**: How can we make it feel alive?<br/>
The **tool**: `TIME` and `sin`.

We mentioned `TIME` before. Since time only moves forward, though, it isn't very useful for animation.<br/>
`sin` is a function that takes any number and keeps bouncing its output back and forth in a fixed range, no matter how large the input gets.<br/>
If we combine them, we get an animation!

<ShaderPreview 
  fullShader={`void fragment() {
    float pulse = sin(TIME);
    COLOR = vec4(vec3(pulse), 1.0);
  }`}
  width={150}

Don't look now, but I think that square is winking at you!

Don't get too excited, though! You might want to know each other a bit better before moving forward to anything serious.
For example, you probably didn't notice yet that its winks are not even. Black lingers way longer than white does.

The issue is that `sin` is a function returning values between -1 and 1. But your screen can't display <Hint message="What would that even look like?">a color value below 0.0</Hint>, so anything negative is painted as a pure black.

To keep the `sin` between 0 and 1, we can nudge the initial range with some operations, in this case, for example: `* 0.5 + 0.5`.
How I got to those numbers <Hint message="Though, they can be easily checked by applying them over both edges of the [-1,1] interval.">doesn't really matter</Hint>. We'll figure a way to intuitively find those later.

Here's a cleaner pulsing pattern!

<ShaderPreview

    COLOR = vec4(vec3(pulse), 1.0);
